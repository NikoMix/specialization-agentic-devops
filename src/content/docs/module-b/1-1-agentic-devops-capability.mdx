## What the Auditor Checks

The auditor verifies that your organisation has **demonstrated technical capability** in designing and delivering modern, AI-assisted SDLC platforms on Microsoft Azure + GitHub Enterprise Cloud — not just knowledge, but practical delivery experience.

**Typical questions:**

- Can you demonstrate end-to-end Agentic DevOps delivery for real customers (Copilot adoption, GHAS roll-out, ARC runner pools, Azure DevOps → GitHub migration, custom MCP agents)?
- Which GitHub Enterprise + Azure services has your team used in production engagements?
- Do you have reference architectures and reusable delivery assets?

  Case studies should explicitly reference the GitHub and Azure services used

  federation). Generic "DevOps transformation" descriptions without specific
  product references are weak evidence.
</Aside>

## Evidence Guidance

### Case Study Structure

Each case study should include:

```markdown
## Customer: [Customer A / Full name with consent]
**Industry:** [e.g., Financial Services]
**Challenge:** [Brief description of the SDLC / security / agent problem]
**Solution:**
- GitHub services used: [GHEC, Copilot Enterprise, GHAS, Actions, MCP server X...]
- Azure services used: [AKS for ARC runners, Key Vault, Entra ID workload identity, Defender for Cloud...]
- Architecture overview: [2–3 sentences]
- Integration points: [e.g., migrated from Azure DevOps; integrated with Defender]
**Outcome:**
- PR cycle time delta: e.g. -38%
- Copilot acceptance rate: e.g. 31%
- GHAS critical findings before / after: e.g. 47 → 0 in 30 days
- Pipeline reliability: e.g. green-build rate 92% → 98%
**Delivery timeline:** [e.g., 10 weeks from kickoff to scale-out]
**Your team's role:** [Lead architect + delivery management / Implementation partner]
```

### Architecture Diagrams

Diagrams should clearly show:

- GitHub Enterprise Cloud (orgs, EMU, SSO, audit log streaming)
- GHAS surface (code scanning, secret scanning, Dependabot)
- Runner topology (Microsoft-hosted vs. ARC vs. VMSS)
- OIDC federation to Azure (workload identity)
- Copilot / agent permission model (GitHub App, MCP server scopes, network egress)
- Secret model (Key Vault, environment vs. organisation secrets)

**Tools:** Microsoft Visio, draw.io, Lucidchart, Azure Architecture Center templates.

### Capability Statement

A 1–2 page document listing:

- GitHub products your team is qualified to deliver
- Azure services used to host GitHub runners and back agent workloads
- Number of completed engagements per service area
- Key team members and their relevant certifications
- Partner competencies and designations

## Common Gaps

| Gap | Remediation |
|---|---|
| Case studies exist but don't mention specific GitHub / Azure services | Rewrite or annotate to explicitly list the services used |
| All case studies are from one industry | Identify a customer from a different industry — even a small Copilot pilot counts |
| Architecture diagrams are high-level only | Add a detailed view showing runner topology, OIDC federation, and Key Vault paths |
| No measurable outcomes | Use Copilot admin metrics + GHAS finding counts + pipeline reliability deltas |
